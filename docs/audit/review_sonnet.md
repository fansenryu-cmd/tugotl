### 1-2. 결론

현재 상태는 "작가 본인이 자기 논문 몇 편을 결과 확인하며 쓰는 도구"로는 쓸 만하다. 그러나 **연구자 일반에게 배포할 수준은 아니다.** 이유 두 가지:

1. **조용히 틀리는 결함**이 있다. 각주 표시가 문장 안쪽으로 1~3자 당겨져 찍힌다(예: "실정이[3]다."). 개수·본문 글자는 맞으므로 도구의 검증이 모두 "통과"로 나온다(batch 점수 100/100). 사용자는 한글에서 일일이 확인하지 않으면 모른다. 원고 표본 5편 중 5편 모두에서 발생.
2. **복구 불능 상태**가 쉽게 만들어진다. `localStorage` 의 사용자 학회 항목 하나가 깨지면 앱이 시작 단계에서 죽고, `file://` 로 쓰는 사용자는 브라우저 사이트 데이터를 직접 지우는 방법밖에 없다. "학회 JSON을 주고받아 공유"하는 것이 제품 흐름이라 현실적인 위험이다.

다행히 둘 다 고치기 쉽다(§3 F-01, F-03). 보안 쪽은 구조적으로 건전하다(남이 만든 원고가 스크립트 실행으로 이어지는 경로는 찾지 못함).

### 1-3. HTML vs 별도 프로그램 판정

**단일 HTML 방식을 유지하되, "18.5 MB 메일 첨부" 배포는 그만두고 ① HTTPS 정적 호스팅(오프라인 설치 가능한 PWA) ② 압축한 오프라인 판(7.9 MB zip + SHA-256) 의 두 가지로 낸다.** Electron은 비추천, Tauri/네이티브는 지금은 이르다(전환 조건은 §4).
근거 요약: 학교·연구실 PC는 설치 권한이 없는 경우가 많고, 서명 없는 .exe는 SmartScreen에서 HTML보다 훨씬 더 큰 마찰을 일으킨다. 보안 모델도 브라우저 샌드박스가 더 낫다. 현재 문제(무결성·업데이트·메일 한도)는 "호스팅 + 해시 공지"로 대부분 풀리고 코드 재작성이 필요 없다. 상세는 §4.

### F-01 [높음 · 변환 정확성] 각주 표시 위치가 어긋난다 — 실제 논문 5편 각주 179개 중 59개(33%)

- 위치: `src/parse.js:54` (`d.getCharIndexAtStreamPos(0, i, c.pos)`)
- 증상: 한 문단에 각주가 둘 이상일 때, k번째(0부터) 각주는 **k글자 앞**으로 당겨진다. 최대 3자 어긋남을 관측. 첫 각주는 정확.
  - 원본 `실정이다.[각주]` → 산출 `실정이[각주]다.`
  - 원본 `기 어렵다.[각주]` → 산출 `어[각주]렵다.` 가 아니라 3자 앞(`…포용하[각주]기 어렵다.`)
- 원인: rhwp의 `getCharIndexAtStreamPos` 가 앞선 컨트롤 수만큼 글자 위치를 덜 센다. 같은 문단에서 `getControlTextPositions(sec, para)` 는 정확하다. 실제 논문 paper1의 15번 문단:

  | 방법 | 각주 4개 위치 |
  |---|---|
  | `getCharIndexAtStreamPos` (현재 코드) | 99, 217, 311, 471 |
  | `getControlTextPositions` | 99, 218, 313, 474 |
  | HWPX 내보내기 XML을 직접 세어 본 값(독립 검증) | 99, 218, 313, 474 |

- 집계(5편 전수): paper1 29/61, paper2 6/39, paper3 12/35, paper4 5/17, paper5 7/27 → **59/179 (33.0%)**.
- 왜 아무도 몰랐나: `tools/convert.mjs`·`tools/batch.mjs` 의 검증은 ① 본문 글자 ② 각주 개수·내용 ③ 강조 런 만 본다. **각주가 붙은 위치는 비교하지 않는다.** 그래서 batch 점수가 100/100 으로 나온다(report_sonnet_a.json). `docs/실데이터검증_2026-10-13.md` 의 "각주 위치 그대로" 서술은 사실이 아니다.

- 원인: ① `parse.js:113` 이 런마다 `body.slice(0, rm.index)` 와 `lastIndexOf` 를 해 O(n²). ② `parse.js:99` 의 `<w:p>…</w:p>` 지연 정규식이 닫는 태그가 없으면 끝까지 훑음. ③ 크기·압축비·항목 수 상한이 전혀 없다(`openFile` app.js:219-228). ④ rhwp 쪽 문단·글자 수에 대한 초선형 처리. ⑤ 작업이 Web Worker가 아닌 주 스레드라서 "페이지가 응답하지 않습니다"가 뜬다.
- **정상 입력에서도 변환(적용) 시간이 제곱으로 늘어난다** (`engine.js` 의 문단별 삽입→rhwp 재조판). 합성 원고(koli 바탕틀): 문단 108개 2.4초, 208개 7.1초, 308개 16.2초, 508개 **46.6초**, 1008개 **189초**. 실제 `paper2.hwp`(208문단, 51쪽) 를 Chrome에서 적용하는 데 **21.3초**, `paper1.hwp` 11.7초 걸렸고 그동안 화면이 멈춘다. 학위논문 규모(문단 1천 이상)는 사실상 쓸 수 없다. `tests/원고/한국형판타지…hwp`(문단 28,386개)는 12개 학회 중 **첫 학회 변환이 19분 넘게 끝나지 않아** 중단했다.
- 영향: 악성 파일은 사용자가 직접 열어야만 작동하므로 위험은 "자기 탭 멈춤" 수준(심각도 중간). 다만 정상 원고에서의 지연은 곧 사용성 결함이다.
- [수정] ① 파일 크기 상한(예: 원고 30 MB, DOCX 해제 합계 150 MB, 항목 수 5천)을 `JSZip` 의 `file._data.uncompressedSize` 로 사전 검사. ② DOCX 파서를 선형으로(런 반복 중 `<w:del` 깊이를 누적 변수로 유지, 정규식 대신 SAX 방식 토큰 스캔). ③ 파싱·변환을 Worker로 옮기고 진행률·취소 제공. ④ 변환은 한 문단씩 삽입하지 말고 rhwp의 일괄 입력 경로(예: 문단 묶음 삽입 후 한 번 재조판)를 찾거나, 조판 지연을 끄는 API 확인. 이것이 가장 큰 효과.

### F-07 [중간 · 보안] CSP가 없고, 배포본의 무결성·출처를 확인할 수단이 없다

- 위치: `src/index.html`(meta CSP 없음), `tools/build.mjs`(해시·서명 산출 없음)
- 앱이 "원고를 전송하지 않는다"고 약속하지만, **다른 곳에서 받은 HTML이 바뀌었는지 사용자는 알 수 없다.** 메일·USB로 도는 18 MB 파일에 한 줄만 끼워 넣으면 미발표 원고를 빼 갈 수 있다. 약속의 신뢰는 "파일이 원본이다"에 달려 있다.
- 부분 대책: 아래 CSP를 넣으면 **정상 빌드가 우연히 외부 호출을 하는 사고**는 막는다(변조된 파일은 CSP를 지우면 되므로 완전한 방어는 아님). 이 정책으로 로드→변환→미리보기가 오류 없이 동작함을 확인했다(스냅샷 dist에 meta만 추가해 실험):
  ```html
  <meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline' 'wasm-unsafe-eval'; style-src 'unsafe-inline'; img-src data: blob:; connect-src data:; base-uri 'none'; form-action 'none'; object-src 'none'">
  ```
  (빌드가 인라인 스크립트의 sha256을 계산해 `'unsafe-inline'` 대신 해시를 쓰면 주입된 인라인 스크립트도 막는다. 이 앱은 인라인 이벤트 속성을 쓰지 않아 가능.)
- 배포 무결성: 릴리스마다 SHA-256 을 학회·연구실 공지 채널과 파일명(`투고틀_2026-10-13_ab12cd.html`)에 함께 적고, 가능하면 Sigstore/minisign 서명을 붙인다. 호스팅하면(§4) HTTPS+SRI 로 해결.
- 또 하나: 이 HTML은 "큰 base64 덩어리 + `Blob` 다운로드 + `fetch('data:…')`" 라서 메일 보안 장비의 HTML 밀반입(smuggling) 탐지 패턴과 닮았다. 첨부가 격리·차단될 가능성이 있다(탐지 여부는 환경에 따라 다르며 실측하지 못함).

### F-08 [중간 · 보안] 학회 JSON의 `submit.url` 이 검증 없이 `href` 에 들어간다

- 위치: `src/app.js:92`, `:320`, `:330` (같은 파일 `:338`의 `sources` 링크는 `/^https?:/` 로 걸러 안전 — 위 세 곳만 빠졌다)
- [재현] 사용자 학회로 `{"id":"cc","journal":"C","society":"s","submit":{"system":"x","url":"javascript:window.__pwn=1;document.title='PWNED'"}}` 저장 후 선택 → 링크의 `href` 에 그대로 들어감.
  현행 Chrome에서는 `target=_blank` + `noopener` 덕에 클릭하면 `about:blank` 가 열릴 뿐 스크립트가 실행되지 않음을 확인했다(다른 브라우저는 미검증). 그래도 **피싱 링크**(가짜 JAMS 로그인)를 학회 JSON 공유로 심는 것은 막지 못한다. 가져오기 JSON이 곧 신뢰 경계다.
- 내장 데이터 문제: 투고처 주소 47개 중 **23개가 `http://`** (예: `http://koli.jams.or.kr`, 로그인이 필요한 JAMS). 서버가 https로 되돌려 주더라도 첫 요청이 평문이다.
- [수정] `new URL(u)` 로 파싱해 `https:`(필요하면 `http:`)만 허용, 아니면 링크 대신 텍스트로. 내장 주소는 https로 교체.

## 4. 아키텍처 판단: 단일 HTML vs 별도 프로그램

### 4-1. 판정

**단일 HTML(웹 기술) 유지.** 다만 배포 형태를 바꾼다: **(A) HTTPS 정적 호스팅 + PWA(설치·오프라인), (B) 오프라인 판은 zip(7.9 MB)+SHA-256.** Electron은 비추천, Tauri는 "자동 업데이트·일괄 처리·대형 학위논문"이 필요해질 때 재검토.

### 4-3. 18.5 MB HTML 메일·USB 배포의 문제

- **크기**: 19,429,203 B. 메일은 첨부를 base64로 부풀리므로 약 25.9 MB가 되어 Gmail 25 MB 한도를 넘고, 국내 웹메일 일반 첨부(예: 20 MB 안팎)에도 걸린다(서비스별 정책은 바뀔 수 있어 확인 필요). zip으로 묶으면 **7.9 MB**(gzip 7.8 MB)라 문제가 사라진다 — HTML 안의 base64가 압축률이 좋기 때문.
- **보안 장비**: base64 덩어리+Blob 다운로드 구조가 HTML smuggling 탐지와 비슷해 격리될 수 있음(미검증). `.html` 첨부를 아예 막는 곳도 있다 → zip이 한 겹 더 낫고, 호스팅이 가장 낫다.
- **무결성**: 서명이 없어 USB·메일로 돌다 바뀌어도 알 수 없음(F-07). 해시 공지 필수.
- **로딩/메모리**: 실측 로드 0.6초, JS 힙 38 MB — 문제 없음. base64 → 바이트 디코드를 위해 한시적으로 문자열이 여러 벌 생기므로(15.7 MB 텍스트) 저사양 PC·모바일 탭에서만 주의.
- **WASM 8 MB 제한 우회 방식**: WASM은 실제 11.8 MB. 비동기 `instantiate` 에 바이트를 넘기는 현재 방식(engine.js:35)은 Chrome의 주 스레드 8 MB 제한을 합법적으로 피하며 Firefox·Safari에서도 동작한다. 적절. 더 줄이려면 base64 대신 gzip+`DecompressionStream`으로 바이트 크기 자체를 줄일 수 있다(HTML 10 MB 안팎). 다만 근본 해법은 호스팅이다.
- **`file://` 제약**: 쿠키·IndexedDB·서비스워커·헤더 CSP 모두 불안정/불가 → 호스팅하면 해결.
- **한계(둘 다 해당)**: 산출 HWP를 실제 한컴오피스에서 연 검증은 이번에 못 했다. rhwp가 쓴 HWP(내부적으로 HWPX 경유 후 재저장)가 한글 2020/2022/2024에서 경고 없이 열리는지는 미검증이므로 배포 전에 필수 확인 항목이다.

### 4-4. 별도 프로그램으로 바꿀 조건

(1) 문단 1천 개 이상 학위논문을 쓰게 되어 Worker로도 느릴 때 → Rust 네이티브 rhwp(Tauri), (2) 학회 폴더 일괄 변환·자동 업데이트가 요구될 때, (3) 한글 프로그램과 직접 연동(자동 열기)이 필요할 때. 그 전에는 비용 대비 이득이 작다.
