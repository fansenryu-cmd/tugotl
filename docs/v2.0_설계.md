# 투고틀 v2.0 설계 — 각주 구분선, Word 출력, 외부 도구 검토

작성 2026-10-25. 계기는 구보학회 투고를 준비하던 이용자의 보고였다. 한글에서 각주를 달면 본문과 각주 사이에 자동으로 생기는 구분선이 투고틀 산출물에서는 보이지 않는다는 내용이다.

*English summary.* v2.0 fixes two separate causes of the missing footnote separator (an empty default in 156 template-less journals, and a byte-layout bug in the HWP writer of rhwp 0.8.7 that affects every output), adds per-journal separator rules, and adds a Word (DOCX) export that mirrors the Hangul output. IeumOffice and kordoc were evaluated as outside tools; IeumOffice is used to cross-check the DOCX output, kordoc is noted for future features.

## 1. 재현과 원인

190곳을 같은 원고로 변환해 산출 HWP의 각주 모양을 모두 읽고, 그중 일부는 한글 2024(COM)로 PDF를 만들어 구분선을 쟀다. 원인은 둘이었다.

### 1-1. 바탕틀이 없는 156곳: 구분선 ‘없음’

규정 수치(format)나 일반 양식으로 만드는 학회는 rhwp의 빈 문서에서 시작한다. 빈 문서의 각주 모양은 구분선 종류 NONE, 길이 0, 구분선 위·아래·각주 사이 여백 0, 시작 번호 0이다. 엔진이 이 값을 그대로 두어 한글에서 선이 나오지 않았다. 바탕틀(학회 양식 HWP)이 있는 34곳은 양식의 설정을 물려받아 이 문제가 없었다.

**고침(engine.js `fixFootNotePr`):** 바탕틀이 없거나 학회가 구분선을 따로 정했으면 한글 2024 새 문서의 기본값으로 채운다. 한글로 새 문서를 만들어 각주를 넣고 HWPX로 저장해 읽은 값이다.

| 항목 | 값 |
|---|---|
| 구분선 | 실선, 길이 코드 −1, 0.12 mm, 검정 |
| 구분선 위 여백 | 850 HWPUNIT (3 mm) |
| 구분선 아래 여백 | 567 (2 mm) |
| 각주 사이 여백 | 283 (1 mm) |
| 시작 번호 | 1 |

### 1-2. 모든 산출물: rhwp의 HWP 5.0 각주 모양 레코드 배치

설정을 고친 뒤에도 한글은 길이 코드와 상관없이 단 너비 전체로 선을 그렸다. 한글에서 산출물을 다시 HWPX로 저장해 보니 구분선 길이가 55,711,269 같은 값으로 읽혔다. 16진수로 0x0352_1625이고, 아래 16비트가 넣은 길이(5669), 위 16비트가 다음 칸인 구분선 위 여백(850)이다.

각주·미주 모양 레코드(HWPTAG_FOOTNOTE_SHAPE, 28바이트)를 바이트로 비교했다.

| 바이트 | 한글 2024가 저장한 파일 | rhwp 0.8.7이 저장한 파일 |
|---|---|---|
| 12–15 | 구분선 길이 i32 (`ff ff ff ff`) | 길이 i16 (`ff ff`) + 위 여백 (`52 03`) |
| 16–17 | 구분선 위 여백 (`52 03`) | 0 (`00 00`) |
| 18–19 | 구분선 아래 여백 | 아래 여백 |
| 20–21 | 각주 사이 여백 | 각주 사이 여백 |
| 22–27 | 선 종류·굵기·색 | 같음 |

rhwp 소스(`src/serializer/control.rs`의 `serialize_footnote_shape`)도 “HWP5 노트 구분선 길이는 i16 슬롯”이라는 가정으로 2바이트를 쓴다. 한글 자신은 4바이트로 쓰고 읽는다. 그래서 한글은 길이를 엄청난 값으로 읽어 단 너비로 자르고, 구분선 위 여백을 0으로 읽는다. 한글 판이나 뷰어에 따라 이런 값에서 선을 그리지 않을 수 있다. 저장소의 바탕틀도 예전에 rhwp로 정제해 저장했기 때문에 같은 배치였다.

**고침(src/hwpfix.js):** 저장 직후 HWP 복합 파일을 열어 `BodyText/Section*` 스트림을 풀고 이 레코드의 12–17바이트를 한글 배치로 고친 뒤 다시 묶는다. 복합 파일은 cfb(SheetJS, Apache-2.0), 압축은 pako(MIT)로 다룬다. 16–17바이트가 0이 아니면 이미 한글 배치이거나 모르는 배치로 보고 손대지 않는다. rhwp를 올릴 때는 이 고침이 여전히 필요한지 `fnrec_all` 검사로 다시 확인한다.

### 1-3. 한글의 구분선 길이 코드

고친 파일을 한글 2024로 그려 잰 값이다(본문 너비 313pt 문서).

| 길이 코드 | 한글이 그린 길이 |
|---|---|
| −1 (한글 기본) | 5 cm (141.8 pt) |
| −2 | 2 cm |
| −3 | 단 너비의 1/3 |
| −4 | 단 너비 전체 |
| 양수 | 그 값(HWPUNIT, 7200 = 1인치) |

rhwp 미리보기도 −1을 5cm, −2를 2cm로 그려 한글과 같다.

### 1-4. 시험

- 190곳 × 원고 2편: 산출 HWP의 각주 모양 레코드가 모두 한글 배치이고, 학회 양식의 길이·간격 값이 그대로 남았다.
- 한글 2024로 20곳을 그려 각주가 있는 쪽마다 구분선을 찾았다. 모두 양식대로 나왔다(5 cm, 2 cm, 단의 1/3, 단 전체). 앞 쪽에서 이어진 각주가 맨 위에 오는 쪽은 검사기가 선을 못 찾았지만 그림으로 보면 선이 있었다.
- 회귀 시험(pipeline·fidelity 12/12·verify_matrix 190/190)은 그대로 통과했다.

**보고 사례와의 관계.** 구보학회는 바탕틀이 있어 1-1에는 해당하지 않고 1-2에 해당한다. 한글 2024에서는 선이 단 너비로 그려지고 선 위 여백이 0이었다. 보고한 분의 한글 판이나 뷰어에서는 이 잘못된 값 때문에 선이 그려지지 않았을 가능성이 크다. v2.0 산출물로 다시 확인을 부탁한다.

## 3. Word(DOCX)로 저장

Word로 받는 학회, 해외 공동 저자, 한글이 없는 환경을 위해 ▾ 메뉴에 ‘Word(DOCX)로 저장’을 넣었다. 투고틀의 한글 산출물(HWPX)을 읽어 같은 서식의 Word 문서로 옮긴다(src/hwpx2docx.js). 그래서 190곳 모두 학회 양식이 그대로 Word에 들어간다.

### 3-1. 옮기는 것

| 한글 | Word |
|---|---|
| 용지·여백 | 쪽 크기·여백. 한글은 본문이 ‘위쪽 + 머리말’ 아래에서 시작하므로 Word 위쪽 여백 = 위쪽 + 머리말, 머리말 거리 = 위쪽(아래쪽도 같음) |
| 글꼴(한글·영문 따로)·크기·굵게·기울임·밑줄·취소선·위첨자·색 | 같은 속성. 한글 글꼴은 동아시아 글꼴로, 따옴표 같은 모호한 문자도 한글 글꼴로(hint) |
| 장평·자간 | 문자 폭 비율·문자 간격(자간 %를 글자 크기에 곱해 pt로) |
| 줄 간격 비율 n% | ‘최소 n% × 글자 크기’ |
| 들여쓰기·내어쓰기·좌우 여백·문단 위아래 간격·정렬·쪽 나눔 | 같은 속성. 한글식 내어쓰기(여백 그대로, 다음 줄만 밂)는 Word의 왼쪽 + hanging |
| 각주 | Word 각주. 번호 꼴의 뒤 장식(‘1)’의 ‘)’)과 번호 없는 각주(‘*’ 표시)도 옮김 |
| 각주 구분선·간격 | 위 테두리를 그린 빈 문단으로 길이(5 cm·2 cm·1/3·전체)·굵기·색을 맞추고, 구분선 위·아래·각주 사이 여백도 옮김 |
| 표 | 칸 합치기(가로·세로), 칸 테두리·음영, 칸 속 각주, 칸 속 표, 캡션 |
| 그림 | 같은 크기의 그림(글자처럼) |
| 쪽 번호 | 꼬리말 쪽 번호 |

### 3-2. 빈칸·크기·줄 간격 보정

Word에서 한글과 같은 쪽 배치를 얻으려고 실측으로 맞춘 것들이다.
- **글자 크기:** Word는 0.5pt 단위만 쓴다(10.3pt → 10.5pt). 반올림으로 넓어진 폭을 장평으로 되돌린다(10.3pt·장평 95% → 10.5pt·장평 93%).
- **줄 간격:** 한글의 비율 줄 간격은 글자 크기 기준이라 글꼴 고유 줄 높이보다 작아질 수 있다(바탕 9pt·132% = 11.9pt). Word의 ‘최소’는 그 아래로 못 내려가므로 글 문단은 ‘고정’으로 쓴다. 그림이 든 문단은 그림이 잘리지 않게 ‘최소’로 둔다.
- **한글·영문 자동 간격:** Word는 기본으로 켜져 있고(‘2013 년’) 한글 양식은 대개 꺼져 있어, 문단 모양의 값을 그대로 옮긴다.


- **빈칸:** 한글은 빈칸을 대략 글자 크기의 절반(0.5 em)으로 그리고, Word는 글꼴의 빈칸(한컴바탕 0.30 em, 바탕 0.33 em)을 쓴다. 그대로 두면 Word가 한 줄에 7%쯤 더 넣는다. 빈칸 런에만 자간 0.17 em을 더했다(문단 끝 줄 실측: 한글 5.04 pt, 보정한 Word 5.0 pt 안팎).

### 3-3. 검증

- **Word 16(COM):** DOCX를 열어 쪽·각주·표·그림 수를 세고 PDF로 저장했다. 190곳 전수 결과는 4절에 있다.
- **한글 산출물과의 쪽 수:** 같은 원고(각주 35개)로 한글·Word 쪽 수를 비교했다(최종 변환기).

| 학회 | 한글 | Word |
|---|---|---|
| 구보학보(gubo) | 35 | 35 |
| 김동명문학연구(kdm) | 36 | 36 |
| 한국언어문화(klnc) | 33 | 32 |
| 탐라문화(tamla) | 37 | 37 |
| 한류연구(jkr, Times New Roman 12pt 200%) | 35 | 37 |

- **줄 높이:** 같은 문단의 줄 간격이 한글 17.02 pt, Word 17.04 pt로 같다.
- **구분선 길이:** 한글과 Word가 같다(5 cm 142 pt / 145 pt, 단 너비 전체 419 / 422 pt, 로컬리티 회색 0.5 mm).
- **이음 오피스(IeumOffice 0.12.4) 렌더러:** Word가 아닌 다른 엔진에서도 DOCX가 깨지지 않는지 보려고 `ieumoffice render`로 쪽 그림을 만들었다. 표 합치기·각주·그림이 나왔다. 각주 칸 번호를 위첨자로 그리는 차이가 있어 번호 런에 기준선을 명시했다.

### 3-4. 한계

- Word는 한국어 문장을 어절 단위로만 줄을 나눠 쪽 수가 한두 쪽 늘 수 있다(190곳 평균 +2.5%, 최대 +4쪽).
- 수식·도형(글상자 제외)은 옮기지 않는다. 경고로 알린다.
- 학회 양식 글꼴이 PC에 없으면 Word가 다른 글꼴로 바꿔 보여 준다. 글꼴 표에 계열·문자 집합·PANOSE를 적었지만 Word는 없는 영문 글꼴을 Calibri로 바꾸기도 한다. 한글도 없는 글꼴은 대체한다. 학회 양식 글꼴을 설치하는 것이 정답이다.
- 머리말·꼬리말의 글(쪽 번호 외)은 아직 옮기지 않는다.

## 5. 외부 도구 검토

### 5-1. 이음 오피스(IeumOffice 0.12.4)

- 정체: pblsketch가 만든 무료 데스크톱 오피스. Mainfunc의 GenOffice(Apache-2.0)를 바탕으로 했고 Apache-2.0으로 공개(github.com/pblsketch/openoffice). 설치 파일은 코드 서명이 없다. 이번에는 설치하지 않고 압축만 풀어 명령줄 도구를 썼다.
- 한글 편집기는 투고틀과 같은 rhwp 기반이다. 따라서 한글 파일의 독립 검증 도구는 되지 못한다. 명령줄 도구의 한글 기능도 글 읽기(`hwp read`)뿐이다.
- Word·PDF 엔진은 따로 있어 DOCX 만들기·읽기·편집·PDF 변환·쪽 그림(`render`)을 할 수 있다. 그래서 v2.0의 DOCX 산출물을 Word가 아닌 엔진으로 교차 확인하는 데 썼다.
- 투고틀에 코드를 들여오지 않았다. 단일 HTML·오프라인이라는 전제와 맞지 않는 큰 Electron·TypeScript 구성이기 때문이다.

### 5-2. kordoc(chrisryugj, MIT, 4.24.5)

- 한국 공공 문서용 파서·생성기(HWP 3·5, HWPX, HWPML, PDF, Word 등 → Markdown·구조 데이터, Markdown → HWPX, 양식 채우기, 신구대조, 개인정보 가림, 렌더). Node 20 이상.
- 확인한 점: HWPX를 만들 때 쓰는 각주 기본값이 투고틀의 새 기본값과 같다(실선, −1, 0.12 mm). 복합 파일도 같은 cfb 1.2.2로 다룬다. HWP5 각주 모양 레코드를 직접 고치는 코드는 없다.
- 투고틀에 쓸 만한 것(다음 판 후보):
  1. **수정 대조표:** 심사 뒤 수정 원고를 낼 때 학회가 요구하는 ‘수정 대조표(수정 전·후)’를 두 원고의 문단 비교로 만든다. kordoc의 신구대조(블록·칸 단위 비교) 발상을 투고틀 안에서 다시 구현한다.

## 6. rhwp에 알릴 결함(초안)

> **HWP5 FOOTNOTE_SHAPE: separator length is written as i16 but Hangul reads i32**
>
> `serialize_footnote_shape` writes the separator length as `i16` followed by top margin, a zero `u16`, bottom margin and note spacing. Files saved by Hangul 2024 store the length as `i32` at offset 12, then top margin (16), bottom margin (18), note spacing (20). When Hangul opens an rhwp-saved file it reads the length as `(top_margin << 16) | length` (e.g. 5669 → 55711269), draws the separator at full column width and treats the top margin as 0. Re-saving such a file from Hangul as HWPX shows `<hp:noteLine length="55711269">`. Writing the length as `i32` and dropping the extra `u16` gives byte-identical records to Hangul's own output. Hangul's length codes: −1 = 5 cm, −2 = 2 cm, −3 = one third of the column, −4 = full column, positive = HWPUNIT.

외부 게시물이므로 저자 확인 뒤 올린다.
